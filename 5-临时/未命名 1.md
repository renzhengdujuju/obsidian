### 一、SRE 核心理念与体系设计

SRE 面试不仅考察技术细节，更看重对稳定性保障体系的理解。核心在于如何通过工程化手段解决运维问题，平衡风险与迭代速度。

|核心概念|定义与关键点|面试回答策略|
|---|---|---|
|**SLI/SLO/SLA**|**SLI** (指标)：衡量服务状态的量化指标（如请求延迟、错误率）。  <br>**SLO** (目标)：SLI 的具体目标值（如 99.9% 请求在 200ms 内返回）。  <br>**SLA** (协议)：基于 SLO 达成的商业承诺，未达成需赔偿 。|强调 SLO 是内部工程目标，用于指导发布和容量规划；SLA 是对外合同。面试中应举例说明如何根据业务容忍度制定 SLO。|
|**错误预算 (Error Budget)**|允许系统在特定周期内不可用的时间总量（如 99.9% 可用性对应每月 43 分钟停机时间）。若预算耗尽，必须停止新功能发布，全力修复稳定性 。|阐述错误预算如何作为“刹车机制”，协调开发（追求功能）与运维（追求稳定）的矛盾，体现 SRE 的工程价值。|
|**可观测性 (Observability)**|超越传统监控，包含 **Metrics** (指标)、**Logs** (日志)、**Traces** (链路追踪) 三大支柱，旨在通过外部输出推断系统内部状态 。|区分监控（知道系统坏了）与可观测性（知道为什么坏了）。提及 Prometheus+Grafana+ELK+Jaeger 的组合实践。|
|**混沌工程 (Chaos Engineering)**|在生产环境中主动注入故障（如杀 Pod、断网、延迟），以验证系统的容错能力和恢复流程 。|强调目的是建立对系统韧性的信心，而非单纯破坏。提及 ChaosBlade 或 ChaosMesh 等工具。|

### 二、Linux 系统与网络底层原理

SRE 需要具备深厚的操作系统功底，能够处理复杂的性能瓶颈和底层故障。

#### 1. 进程管理与通信

- **进程状态转换**：重点掌握 `Running`, `Sleeping`, `Stopped`, `Zombie` (僵尸进程) 状态。僵尸进程是子进程结束但父进程未回收资源导致的，需通过杀死父进程或重写代码处理 。
    
- **进程通信 (IPC)**：常见方式包括管道 (Pipe)、消息队列、共享内存 (最快)、信号量、套接字 (Socket)。面试中常问共享内存为何最快（无需内核态拷贝）。
    
- **Load Average 含义**：表示单位时间内活跃进程数（运行中 + 不可中断睡眠 D 状态）。若 Load 高但 CPU 使用率低，通常意味着大量进程在等待 IO 。
    

#### 2. 网络协议与故障排查

- **TCP 三次握手与四次挥手**： * **握手**：SYN -> SYN+ACK -> ACK。第二次握手时服务器分配资源，防范 SYN Flood 攻击需调整内核参数 (`tcp_max_syn_backlog`) 。
    
    - **挥手**：FIN -> ACK -> FIN -> ACK。`TIME_WAIT` 状态出现在主动关闭方，持续 2MSL，防止旧报文干扰新连接。高并发下需优化 `tcp_tw_reuse` 。
        
- **DNS 解析过程与劫持**：本地 Hosts -> 本地 DNS 缓存 -> 递归 DNS -> 根/顶级/权威域名服务器。劫持通常发生在递归 DNS 环节，可通过 DNSSEC 或 HTTPDNS 缓解 。
    
- **用户访问网站全流程**：DNS 解析 -> TCP 连接 -> TLS 握手 (HTTPS) -> HTTP 请求 -> Nginx 反向代理 -> 后端应用 (Tomcat/Go) -> 数据库/缓存 -> 返回响应 。
    

#### 3. 文件系统与 IO

- **Inode 与文件描述符**：Inode 存储文件元数据（权限、大小、指针），文件名仅指向 Inode。删除文件后若进程仍持有句柄，空间不会释放，需重启进程或清空 `/proc/<pid>/fd/<fd>` 。
    
- **RAID 级别**：RAID 0 (性能无冗余), RAID 1 (镜像冗余), RAID 5 (奇偶校验，允许坏一块盘), RAID 10 (镜像 + 条带，高性能高可靠) 。
    

### 三、容器化与 Kubernetes 深度实践

云原生时代，K8s 是 SRE 的必考项，重点在于调度原理、故障排查及安全模型。

#### 1. 核心组件与原理

- **Docker 原理**：基于 Namespace (隔离视图：PID, Net, Mount 等) 和 Cgroups (资源限制：CPU, Memory) 实现轻量级虚拟化。UnionFS (联合文件系统) 实现分层存储 。
    
- **K8s 认证与授权**：
    
- **认证**：API Server 支持证书、Token、OIDC 等。  
    * **授权**：RBAC (基于角色的访问控制) 是最常用模式，定义 Role/ClusterRole 与 RoleBinding 。
    
- **Sidecar 模式演进**：传统 Service Mesh (如 Istio) 使用 Sidecar 代理流量，但存在资源开销大、升级复杂问题。新一代方案趋向于 eBPF (如 Cilium) 或 Ambient Mesh架构，将代理能力下沉到内核或节点层级 。
    

#### 2. 高级调度与安全

- **Gang 调度**：用于 AI/大数据场景，要求一组 Pod 要么全部调度成功，要么全部不调度，避免资源死锁 。
    
- **DRA (Dynamic Resource Allocation)**：K8s 1.35+ 特性，动态分配 GPU 等稀缺资源，替代静态 Device Plugin 模式，提升资源利用率 。
    
- **PSS (Pod Security Standards)**：替代旧的 PSP (Pod Security Policy)，提供 Privileged, Baseline, Restricted 三个安全基线，强制约束 Pod 的安全上下文 。

### 四、自动化运维与开发能力

SRE 强调 “Toil” (琐事) 的自动化，必须具备编程能力（Python/Go）及 IaC (Infrastructure as Code) 经验。

#### 1. Python 进阶考点

- **装饰器 (Decorator)**：用于在不修改原代码基础上增加功能（如日志记录、重试机制、权限校验）。
    
    - _原理_：高阶函数，接收函数作为参数并返回新函数 。
        
- **GIL (全局解释器锁)**：CPython 中同一时刻只有一个线程执行字节码，导致多线程无法利用多核 CPU。IO 密集型任务可用多线程，CPU 密集型需用多进程或多协程 。
    

#### 2. 自动化脚本示例：基于装饰器的重试机制

针对网络波动导致的临时故障，实现自动重试逻辑是 SRE 常见需求。
Python
```
import time
import functools
import random

def retry_on_failure(max_attempts=3, delay=2):
    """
    装饰器：当函数抛出异常时自动重试
    参数：max_attempts 最大尝试次数，delay 每次重试间隔秒数 """
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise e  # 达到最大次数仍失败，抛出异常
                    print(f"执行失败 (尝试 {attempt}/{max_attempts}): {e}. {delay}秒后重试...")
                    time.sleep(delay)
        return wrapper
 return decorator

@retry_on_failure(max_attempts=3, delay=1)
def fetch_monitor_data(api_url): # 模拟网络请求不稳定
    if random.random() < 0.7:
        raise ConnectionError("网络连接超时")
    return {"status": "success", "data": "monitor_metrics"}

# 调用示例
if __name__ == "__main__":
    try:
        result = fetch_monitor_data("http://prometheus-api/metrics")
 print(f"获取成功：{result}")
    except Exception as e:
        print(f"最终失败：{e}")
```

#### 3. 配置管理与 GitOps

- **Ansible**：基于 SSH 的无代理自动化运维工具。核心概念包括 Inventory (主机清单), Playbook (YAML 编排), Module (模块)。常用于批量配置下发、补丁更新 。
    
- **GitOps**：以 Git 仓库为唯一事实来源，通过 ArgoCD 或 Flux 等控制器自动同步集群状态。优势在于版本可控、回滚迅速、审计方便 。
    

### 五、故障排查方法论与开放性问题

面试官常通过场景题考察候选人的逻辑思维和经验沉淀。

| 场景问题             | 排查思路与核心要点                                                                                                                                                                                                  |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CPU 使用率 100%** | 1. `top` 定位高占用进程 PID。  <br>2. `top -Hp <PID>` 定位具体线程 ID (TID)。  <br>3. `printf "%x\n" <TID>` 转换为十六进制。  <br>4. `jstack <PID> \| grep <hex_tid> -A 20` (Java) 或 `perf top -p <PID>` (通用) 查看堆栈，定位死循环或密集计算代码 。 |
| **磁盘空间未满但无法写入**  | 1. 检查 Inode 使用率 (`df -i`)，小文件过多可能耗尽 Inode。  <br>2. 检查是否有已删除但未释放句柄的大文件 (`lsof \| grep deleted`)，需重启进程释放 。                                                                                                   |
| **服务间歇性超时**      | 1. 检查依赖组件 (DB/Redis) 慢查询日志。  <br>2. 分析网络丢包与重传 (`netstat -s`, `tcpdump`)。  <br>3. 检查 GC 停顿时间 (Full GC)或 线程池满队列情况。  <br>4. 结合 Trace 链路追踪定位耗时环节 。                                                             |
| **如何设计监控告警体系**   | 1. **分层监控**：基础设施 (Node) -> 容器 (Pod) -> 应用 (JVM/Go Runtime) -> 业务 (订单量/支付成功率)。  <br>2. **告警分级**：P0 (电话/短信，立即响应), P1 (IM 通知，30 分钟内), P2 (邮件/工单，工作时间处理)。  <br>3. **减少噪音**：设置收敛规则，避免告警风暴，确保告警即行动 。             |
| **线上误操作删库怎么办**   | 1. **止损第一**：立即切断流量或切换只读，防止数据进一步损坏。  <br>2. **评估范围**：确认受影响的时间点和数据量。  <br>3. **恢复数据**：从冷备/热备/Binlog 恢复。  <br>4. **复盘改进**：实施权限最小化原则，高危操作需双人复核 (Four-eyes principle)，引入自动化防误删工具 。                              |
