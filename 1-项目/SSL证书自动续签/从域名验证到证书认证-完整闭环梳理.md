# 从域名验证到证书认证：完整闭环梳理

> 读完原理后直接选一个方案动手：[[执行方案-乐此加密|方案一：乐此加密]]（省事，靠 CNAME 委派）或 [[备选方案-阿里云RAM角色|方案二：阿里云 RAM + acme.sh]]（0 元，靠 TXT 直连）。两个方案**二选一**，不能同时用。

> 本文把 DNS 域名验证（TXT / CNAME）与 SSL/TLS 证书的签发、认证过程串成一个完整闭环。
> 核心区分：**TXT/CNAME 解决"CA 凭什么把证书发给你"，证书认证解决"访问者凭什么相信服务器出示的证书是真的"。**

---

## 一、先记住一个前提：DNS 就是"电话簿"

上网时输入 `blog.example.com`，电脑不知道它在哪，于是去查 DNS（电话簿），查到对应的 IP 地址（电话号码），才能建立连接。

DNS 电话簿里有很多种"条目类型"，本文涉及两种：

| 类型 | 比喻 | 作用 |
|---|---|---|
| **CNAME** | 电话簿里的"请转接" | 这个域名不直接用，请转接到另一个域名去查 IP |
| **TXT** | 电话簿里的"备注栏" | 往域名下贴一段纯文本，谁查都能读到，不指向任何地方 |

---

## 二、CNAME：电话簿里的"请转接"

### 生活比喻

打电话到总机找张三，总机说："张三不在这儿，你打另一个号码找他。"于是你拨新号码，找到了张三。

CNAME 就是电话簿里写的这句话：**"这个号码不直接用，请转接到另一个号码。"**

### 实际发生的事（以 `blog.example.com` 指向 `example.github.io` 为例）

1. 访问者查电话簿："`blog.example.com` 的电话是多少？"
2. 电话簿说："别问我，去查 `example.github.io`。"
3. 继续查 `example.github.io`，拿到真实 IP。
4. 访问者**直接连到这个 IP**，网站打开。

**关键点：**
- 浏览器从头到尾以为自己在访问 `blog.example.com`，不知道中间转过一次接。
- CNAME 只发生在 **DNS 解析阶段**，不参与实际连接。
- 证书和私钥放在**最终那台服务器**上，CNAME 本身不携带任何证书信息。

### CNAME 的第二种用法：把"验证"这件事也转接出去

CNAME 不只是"转接到服务器 IP"。证书验证里还有一种用法：**把 `_acme-challenge` 这个名字用 CNAME 指向第三方**，等于说"验证域名这件事，请去找第三方办"。

这就是 [[执行方案-乐此加密|方案一（乐此加密）]] 的原理：你在自己的 DNS 里写一条 CNAME 指向乐此的服务器，之后 CA 查验证记录时，会顺着这条 CNAME 去问乐此，乐此替你把 TXT 写好。

---

## 三、TXT：电话簿里的"备注栏"

### 生活比喻

电话簿每个号码旁边有一栏**备注**，可以写任何话："这家店周一休息""快递放门口""我是张三本人"。备注不指向任何地方，就是一段给人看的文字，而且可以写好几条，互不冲突。

TXT 记录就是 DNS 电话簿里的这个"备注栏"。

### 它怎么用来验证域名？

1. CA（证书机构）说："你在 `example.com` 的备注栏写一句话：`abc123xyz`。"
2. 你去 DNS 后台添加一条 TXT 记录，值填 `abc123xyz`。
3. CA 去查电话簿，**专门读这个域名的 TXT 备注**，读到 `abc123xyz`，和它下发的一致。
4. 只有真正能改这个电话簿的人才能写这条备注 → CA 确认域名归你管 → 验证通过，发证书。

**关键点：**
- CA 全程**没有访问你的网站**，只是查了一下电话簿的备注栏。
- TXT 验证与你的网站是否上线、服务器是否开放端口**完全无关**。
- 另一种"把随机值放在网页文件里让 CA 来检查"是 **HTTP 文件验证**，不是 TXT 验证；TXT 验证纯粹发生在 DNS 层面。

### 为什么 TXT 可以有多条？

因为备注栏本来就是"可以写好几条、各管各的"：

- 一条写 CA 给的验证码（申请证书用）
- 一条写 Google 给的验证码（接入搜索引擎用）
- 一条写 SPF 规则（声明哪些服务器可以代你发邮件）

TXT 是"信息性"记录，多条并存没有冲突。**但前提是这个名字下没有 CNAME**（见下一节）。

---

## 四、一条必须记住的规则：CNAME 和 TXT 不能共存

DNS 有个硬规定：**同一个名字（比如 `_acme-challenge.ff.example.com`）下，一旦写了 CNAME，就不能再写其他任何记录**（TXT、A、MX 等都算），反过来也一样。

原因：CNAME 的意思是"别管这个名字，去看我指向的那个名字"。如果同一个名字下既有 CNAME 又有 TXT，解析器就不知道该信谁了，于是干脆禁止。

**这条规则直接决定了两个实操方案互斥：**

- 方案一（乐此）在 `_acme-challenge.ff` 上写 **CNAME**；
- 方案二（阿里云 RAM + acme.sh）在 `_acme-challenge.ff` 上写 **TXT**；
- 二者占的是**同一个位置**，只能留一个。切换方案时，必须先删掉旧的、再写新的，还要等 10~30 分钟让旧记录失效。

---

## 五、DNS-01 验证的两种做法（对应两个实操方案）

CA 靠"查 TXT"验证域名，但"这条 TXT 由谁来写"分两种：

### 做法 A：直连 TXT（方案二：阿里云 RAM + acme.sh）

你自己（或你装的工具）直接往自己的 DNS 里写 TXT，CA 直接查你的 DNS。

- 优点：不依赖第三方，0 元。
- 代价：需要能改 DNS 的权限。[[备选方案-阿里云RAM角色|方案二]] 用阿里云 RAM 角色发"临时工牌"，让 acme.sh 每次自动刷工牌去写 TXT，不留长期密码。

### 做法 B：CNAME 委派（方案一：乐此加密）

你把 `_acme-challenge` 用 CNAME 指向第三方（乐此），CA 查你域名时顺着 CNAME 查到第三方，第三方在**它自己的 DNS** 里写 TXT。

- 优点：你只加一次 CNAME，之后验证全由第三方代劳，续期也不用碰阿里云 API。
- 代价：依赖第三方平台，自动续期约 ¥30 一次性。[[执行方案-乐此加密|方案一]] 详细步骤在此。

## 六、用编号体系重述两个场景

设：**1 = 访问者，2 = 电话簿里的转接记录（不是服务器），3 = 最终服务器**

### CNAME 场景（网站托管）

```
1（访问者）→ 查 DNS 电话簿 → 读到 CNAME："请转接到 3 的域名"
→ 1 继续查 3 的域名，拿到 IP
→ 1 直接连到 3，完成 TLS 握手（证书在 3 上）
→ 访问成功
（2 = 电话簿里的转接记录，不参与实际连接）
```

### TXT 验证场景

```
你 → 向 CA 申请证书
→ CA 说："在域名的 TXT 备注里写 abc123xyz"
→ 你去 DNS 后台加 TXT 记录：abc123xyz
→ CA 查 DNS，读 TXT 备注 → 读到 abc123xyz → 确认域名归你
→ CA 发证书 → 你把证书装到 3 上
→ 之后 1 访问 3，正常 HTTPS 握手，访问成功
（TXT 验证全程不涉及 1 和 3，只涉及你和 CA 查电话簿）
```

## 七、证书签发与认证的完整闭环

**TXT/CNAME 解决的是"CA 凭什么把证书发给你"，证书认证解决的是"访问者 1 凭什么相信服务器 3 出示的证书是真的"。**

### 第一步：签发闭环（结合 TXT/CNAME）

证书签发分两段：**你先造一把"锁和钥匙"，CA 给你的"锁"盖个章，证明这锁确实归你。**

1. **生成密钥对**：在服务器上生成**私钥**（自己藏好，绝不外泄）和**公钥**，再生成 CSR（证书签名请求，内含公钥和域名信息）。
2. **域名验证（TXT/CNAME 环节）**：把 CSR 发给 CA。CA 下发挑战值，你通过 **TXT**（直连写）或 **CNAME 委派**（第三方代写）完成应答。CA 查到了，就确认域名归你。
3. **CA 签发证书**：CA 用**它自己的私钥**，对你提交的公钥和域名等信息签名，生成**数字证书**——本质是"CA 认证，这个公钥确实属于 example.com 的主人"。你把证书部署到服务器 3。

至此 **签发闭环** 完成：服务器 3 有私钥，服务器 3 上装好了 CA 签过名的证书（内含公钥）。

### 第二步：认证闭环（访问者 1 如何信任服务器 3）

访问者 1 打开浏览器，连到服务器 3。**证书认证发生在 TLS 握手阶段**，即传输任何网页数据之前。

1. **服务器 3 出示证书**：3 把 CA 签过名的证书发给 1。
2. **1 验证签名（核心）**：1 的浏览器/操作系统里**预装了它信任的 CA 公钥**。1 用这些公钥尝试解密证书上的"签名"，能解开说明证书确实是某个受信任 CA 签发的、内容没被篡改。
3. **1 检查证书内容**：域名对不对？过期没有？签发它的 CA 是不是自己信任的？
4. **握手成功**：全部通过后，1 确认"对面确实是拥有私钥的、被 CA 认证过的服务器 3"，双方协商出会话密钥，后续通信全部加密。

**关键点：** 1 从头到尾**没有去联系 CA 问"这张证书是真的吗"**，它依赖的是系统里预装的信任名单（根证书）和数学签名验证。CA 的权威早在操作系统出厂时就被预装进去了。

## 八、一图总结完整闭环

```
【签发阶段：解决"凭什么发给你"】
你/服务器3 生成密钥对 → 发 CSR 给 CA
        ↓
CA 要求验证域名 → 你加 TXT（直连）或 CNAME（委派）→ CA 查 DNS 确认你是主人
        ↓
CA 用自己私钥给你的公钥签名 → 生成证书 → 你部署到服务器3
        ↓
【认证阶段：解决"凭什么信你"】
访问者1 连上服务器3 → 服务器3 出示证书
        ↓
1 用系统预装的 CA 公钥验证证书签名 → 检查域名/有效期
        ↓
全部通过 → 确认服务器3身份 → 协商会话密钥 → 加密通信开始
```

## 九、为什么要自动化：证书有效期越来越短

手动续签曾经还能忍，现在不行了。国际规定（CA/B Forum SC-081）在持续缩短证书有效期：

| 时间节点 | 单张证书最长有效期 |
|---|---|
| 2026-03-15 之前 | 398 天 |
| 2026-03-15 起 | 200 天 |
| 2027-03-15 起 | 100 天 |
| 2029-03-15 起 | 47 天 |

> 具体日期以 CA/B Forum 最新公告为准。已签发的旧证书不受影响，续签/重签才按新规执行。

配套变化：曾经唯一能签 180 天免费证书的 **Buypass** 已停服（2025 年宣布退出，2026-04-15 ACME 服务终止），所以现在**没有 180 天的免费 ACME 证书了**，主流免费 CA 都是 90 天。

**结论**：证书会越来越短、换得越来越勤，手动续签必然出事。**买一年期证书的时代已经结束，必须自动化。** 这就是本项目要做两套自动续签方案的原因。

## 十、背景补充：方案里的云端角色（那些"奇怪要求"的原因）

两份实操手册里出现了 ECS、VPC、RAM、同账号这些词。这里用大白话把"为什么"一次讲清，读完再回去看方案会更顺。

### ECS：证书到底装在哪

**ECS（云服务器）= 放在阿里云机房里的一台电脑**，有 CPU、内存、硬盘和操作系统，和家用电脑的区别只是它放在机房、按需租用、通过网络远程操作。

三者关系一句话：**域名**是店的名字，**DNS**负责告诉客人店在哪（IP 地址），**ECS**是真正开店干活的地方。证书和私钥就装在 ECS 的 Nginx 里；"网站"是跑在 ECS 上的程序，不是 ECS 本身。

### 为什么方案二要求"DNS 和 ECS 在同一个阿里云账号"

方案二的核心是给 ECS 发一张工牌（RAM 角色）去改 DNS，而**工牌只能管"本账号"的资源**：

- 同账号 → 发一张工牌就够，授权链最短；
- DNS 在账号 A、ECS 在账号 B → 账号 B 的工牌碰不到账号 A 的 DNS，要额外配跨账号信任，复杂好几倍，不值得为这件事上。

> 跨账号不是绝对做不到，而是需要额外配置角色信任 + 权限策略；方案二附录 12.1 给了替代路径。

### 为什么方案二要求"ECS 必须是 VPC 网络"

- **VPC（专有网络）** = 你在阿里云里自己划的一块隔离私人网络，网段自己规划、默认与别人隔离——好比自建小区。
- **经典网络** = 阿里云统一规划管理的大公共网络——好比大杂院，隔离和管理能力弱，已逐步淘汰。

硬性限制：**ECS 实例 RAM 角色只支持 VPC 网络**，经典网络的机器挂不了工牌。所以方案二第 0 步必须先确认这条，不是可选项。

### RAM 家族辨析：角色 ≠ 用户 ≠ 策略

| 名词 | 一句话 | 对应方案二 |
|---|---|---|
| 主账号 | 老板，拥有一切权限 | 通常不直接拿来干活 |
| RAM 用户 | 员工账号，带**长期**密码（AccessKey） | 只有附录 12.1 的备选路径才用到 |
| **RAM 角色** | **临时工牌，本身没有密码**，谁被授权谁能"刷" | 第 1 步创建的 `EcsAutoSslRenew` |
| 权限策略 | 规定工牌**能干什么**（4 个 DNS 动作） | 第 2 步 |
| 信任策略 | 规定**谁有资格**刷这张牌（只允许 ECS 服务） | 第 1 步创建角色时选"信任云服务器 ECS"就是它 |

### STS 临时凭证：刷卡的全过程

1. ECS 上的程序需要调阿里云 API；
2. 程序问本机内置的**元数据服务**（`100.100.100.200`，只有本机够得着的"个人档案柜"）："我身上有哪些工牌？"
3. 档案柜返回**临时通行证**：临时 AccessKeyId + SecurityToken + 过期时间（几小时）；
4. 程序拿通行证调 API，只能干权限策略允许的事；
5. 通行证过期就自动再刷一张。

服务器上从头到尾**没有长期密码**；就算泄露，损失的只是几张几小时后自动作废的通行证——这就是方案二比"写死 AccessKey"安全的根本原因。

### 顺带两个词：安全组、公网/私网 IP

- **安全组** = 服务器的门卫，决定哪些端口、哪些来源 IP 能进出。方案一装客户端前要确认"服务器能访问 letsssl.cn"、面板 8899 不对公网开放，都是在跟它打交道。
- **公网 IP** = 对外的门牌，访客靠它连你；**私网 IP** = 小区内部门牌号，同一 VPC 内机器互访用（数据库等后端服务一般只暴露私网 IP）。

## 十一、一句话总结

- **CNAME = 转接电话**：查电话簿时多绕一步。在网站托管里是"转到真正的服务器"；在证书验证里是"把验证委派给第三方"（方案一乐此）。
- **TXT = 备注栏**：贴一段文字，CA 靠读它确认域名归你管。跟网站、服务器、网页文件无关（方案二阿里云）。
- **CNAME 与 TXT 在同一名字下互斥**：所以两个方案只能二选一。
- **TXT/CNAME 属于签发闭环的一环**；访问者看到的"小锁"图标是认证闭环成功的结果。两者共同保证：证书确实是发给你的，且访问者确实是在和你通信。
